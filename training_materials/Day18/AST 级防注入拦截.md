# AST 级防注入拦截

**AST = Abstract Syntax Tree，抽象语法树** 不是原始字符串匹配，而是把一段代码/SQL文本**解析成结构化语法树**，理解语句真实语义、语法结构。

> AST级拦截：**不只是简单关键词字符串匹配**（like 搜 `drop`、`union`）；而是解析语法树，看懂这段SQL/代码到底要做什么操作，从语法结构上识别注入攻击。

## 传统简单防注入（字符串匹配，缺点很大）

比如写正则，只要文本包含 `DROP`、`DELETE`、`UNION` 就拦截。
❌ 容易绕过：大小写变形、注释拆分、编码变形

```
dr/**/op table user; -- 简单字符串检测直接失效
```

## AST 级拦截

1. 将传入的SQL语句，交给SQL解析器，**编译生成抽象语法树AST**

2. 遍历语法树节点，识别里面的语法元素：表名、操作类型（SELECT/DROP/ALTER）、子查询、UNION、权限高危节点

3. **基于语法树规则拦截**，而不是看文字
   
   > 例子规则：
   > 
   > - 不允许出现 `DROP / ALTER / TRUNCATE` 语法节点
   > - 不允许UNION子查询节点
   > - 只允许单条SELECT，禁止多语句（`;` 分隔多条SQL）
   > - 限制只能查询指定业务表，禁止访问系统表

✅ 优势：**很难绕过**。不管攻击者怎么注释、大小写、空格变形，AST解析出来的语法结构不变，高危节点依然会被识别。

## 和参数化查询的关系（重点！很多人混淆）

1. **参数化查询（prepare statement）**：优先方案，**杜绝SQL注入根本手段**，变量和SQL语法完全分离，用户输入永远不能变成SQL语法。
2. **AST拦截**：属于**第二层防护**。
   就算参数化有疏漏、动态拼接表名/排序字段（这类场景没法用参数化），AST解析检查语法树，拦截危险操作。

> 场景：SQLite + LangGraph审计工作流，动态生成SQL查询差旅单据
> 动态拼接表名/列名的时候，没法用参数绑定，就适合增加AST校验做兜底防护。

## 举个直观对比

恶意语句：

```
seLeCt * frOm user -- 大小写混淆
```

- 字符串匹配：很容易绕过
- AST解析：识别这是`SELECT`查询user表，根据你的策略判断是否放行

恶意注入：

```
select * from report; drop table travel;
```

AST会解析出两棵语句树：一条SELECT + 一条DROP，检测到DROP节点直接拦截。

## 局限

AST拦截**不是万能**：

1. 可以拦截**高危语法操作**，但不能拦截合法SQL做的恶意查询（比如合法SELECT导出全部敏感数据）；这类要靠权限、数据策略控制。
2. 需要对应数据库的专用SQL解析器（SQLite有专门parser），通用SQL解析器会有语法兼容成本。

## 总结

> 字符串匹配：看**长得像什么文字** AST级拦截：看懂**语句真实语法结构是什么**，在语法树层面拦截危险操作，防绕过能力强很多。
