## 一、项目概览

**业务一句话**：批量上传 PDF 简历 → 解析 → LLM 归一化 → 确定性规则硬性初筛 → HR 审核入库，附带人才库沉淀、知识库检索与只读招聘 Agent。

### 部署拓扑（compose 双文件：开发 + 生产）

| 容器 | 端口 | 职责 |
|---|---|---|
| `app`（resume-app-service） | 127.0.0.1:18085 → 8000 | 唯一业务入口：9 组路由，编排全流程 |
| `web`（nginx） | 127.0.0.1:5173 → 80 | Vue3 SPA 托管 + `/api` 反代（支持 SSE 不缓冲） |
| `parser`（resume-parser-service） | 8002 | PDF → 文本，无状态，PyMuPDF→pdfplumber→OCR 三级降级 |
| `knowledge`（resume-knowledge-service） | 8001 | 脱敏画像 Wiki 卡片 + Chroma 稠密/BM25 混合检索 + rerank |
| `db` / `db-test` | 5432 / 55432 | PostgreSQL 17 双库；测试库 tmpfs 重建即清 |

### 技术栈

- **后端**：Python 3.12 / FastAPI / Pydantic v2 + JSON Schema 双校验 / SQLAlchemy 2 / SQLAlchemy-Alembic 迁移 / LiteLLM（qwen-plus 文本、qwen-vl-max OCR、qwen3 embedding + reranker）
- **前端**：Vue 3.5 `<script setup>` + TypeScript（vue-tsc 构建期检查）+ Element Plus + Tailwind v4 + Vite，无 Pinia（状态靠 localStorage + 模块级 reactive）
- **检索**：ChromaDB（cosine）+ rank-bm25 + jieba，RRF(k=60) 融合后 rerank 重排
- **工程**：uv workspace monorepo（根 `package=false`，members=`services/*` + `packages/*`，统一 `uv.lock`）、ruff、pytest、GitHub Actions CI（三构建先行 + ruff + alembic + 分服务 pytest）、CD 按 head SHA 打 GHCR 不可变镜像 tag

### 代码规模

主服务 `app_service` 42 个模块（13 个 service + 9 组路由 + 20 张 ORM 表）、前端 23 个源文件 / 11 条路由、parser 与 knowledge 各自独立四层结构、测试 unit 16 + integration 2（782 行全链路 22 用例）、alembic 迁移 5 版。

## 二、总体架构评价

### 结论

**架构本体合理，工程纪律在代码里落实得相当好；真正的病根是“文档腐化”——宪法与规格文档停留在上一代系统，而代码已经往前走了两代。** 另有一批越权/契约/运行时缺陷需要按优先级处理（见第五节）。

### 2.1 做对了的（有证据）

1. **服务拆分维度正确**：parser（模型 IO 重、无状态）、knowledge（检索栈独立、可整体替换）与业务主线 app 分离，是按资源特征切分而非按实体乱拆。弱依赖设计到位——compose 里 `parser: condition: service_started` 配注释“解析服务不可用不应阻止主服务启动（简历落『解析失败』可重试）”，状态机有 1/2 两个失败态承接。
2. **uv workspace 用法是范本级的**：根只做总调度，dev 依赖工作区共享，三个服务不会漂移出四套 requirements；`packages/shared` 把 PDF 校验做成“一处实现、双服务薄封装”（`resume_shared.pdf_validation`，app 与 parser 各自代理委托，语义一致）。
3. **LLM 提取与规则决策的分离贯穿到底**（核查全部通过）：
   - 归一化链路两道校验齐备：`normalize_service.py` 先 `jsonschema.validate`（`RESUME_EXTRACT_SCHEMA`，O(246 行)）再 `ResumeProfileData.model_validate`，失败重试 2 次后转人工；
   - 初筛是纯确定性规则三态（PASS/REJECT/PENDING_REVIEW），全仓 LLM 调用点仅归一化提取与 Agent 对话两处，Agent 的岗位评估工具也回调同一 `evaluate_profile`，不搞第二套逻辑；
   - “信息不足 ≠ 不合格”：信息缺失一律 PENDING_REVIEW，`screen_service.py` 三条规则（学历/年限/技能 rapidfuzz）全程无 LLM；
   - Agent 提案不直接执行：`task_service.decide_action` 审批前全量复核（岗位开放、updated_at 快照比对、规则重算仍 PASS），不满足即 `StaleActionError`。
4. **安全姿态普遍高于同类项目**：`.env` 未被 git 追踪、`.env.example` 全占位符；compose 所有端口只绑 127.0.0.1；上传白名单脱敏无电话/邮箱且 `extra='forbid'`；登录用行锁 + 5 次失败锁 15 分钟 + 未知用户名走 dummy 哈希防时序枚举 + session/csrf 只存哈希；Text2SQL 三重防护（sqlglot AST 白名单、`SET TRANSACTION READ ONLY`、statement_timeout，敏感列只许 IS NULL 布尔信号）。
5. **部署链路成熟**：CI 三镜像构建先行 + ruff + alembic 迁移 + 分服务 pytest；CD 按 head SHA 打不可变 tag，production Environment 审批限定 main + Required reviewers；迁移 baseline 用 `IF NOT EXISTS` 幂等、0004 五步 FK 切换完成 `resume_profiles` 主键合并。
6. **测试策略有想法**：红线行为有专门回归锁定（第一岗 REJECT 不剥夺后续岗机会、信息不足→PENDING 而非 REJECT、null 不编造），已知技能匹配子串互撞缺陷（Java/JavaScript、C/C++）用 `strict=True` 的 xfail 固化——修复后 XPASS 会报错提醒移除标记；`conftest.py` import 期强制 `DATABASE_URL` 指向 55432 测试库、非测试库地址直接拒绝执行，防误清生产库。

### 2.2 值得商榷的（有证据）

1. **文档三重漂移**（详见第三节）：AGENTS.md 引用的两份“真理之源”已在 10-14 被删除；TECH_ARCHITECTURE.md 还在画单服务 `smart-resume/src/` 目录树；8 份 function_specs 通篇引用旧路径。宪法管不住新领土（Agent/人才库/知识库子系统都进了代码但没进 AGENTS.md 的四层描述），红线就开始名存实亡。
2. **api 层越权埋业务**：`api/resume.py` 的 update_profile/confirm_resume/delete_resume（级联删除 + 磁盘清理）、`api/requirements.py` 的需求删除（手工按序级联）直接在 router 里操作 ORM，“api 不直接摸 ORM 之外的 SQL”字面上没破，但“参数校验后调 services”的分层精神已破——这些正是最容易累积烂泥的地方。
3. **跨服务契约只有文档级没有代码级**：parser/knowledge 的请求响应 schema 各自独立定义，互相对齐靠 specs/api 文档 + 契约测试；`packages/shared` 只装了 PDF 校验，最该共享的 schema 没进去。实测已经漂移：`knowledge_client.search_documents` 固定携带 `top_k/document_types/metadata_filter`，而知识库 `SearchRequest` 是 `extra='forbid'`（见第五节高风险项）。
4. **两套环境变量命名**：主服务 `DASHSCOPE_API_KEY/LLM_*`，parser/knowledge `MODEL_API_KEY/MODEL_*`，靠 compose `${MODEL_API_KEY:-${DASHSCOPE_API_KEY:-}}` 双层兜底缝合，能用但配置心智成本实打实。
5. **单实例假设贯穿全链但属自知**：批次进度存 `pipeline.py` 模块级 dict + 锁（代码自注释 MVP），重启即丢（`GET /api/parse/{batch_id}/status` 404）、多 worker 各自为政；架构书自己也写了“多实例需先解决任务分发”。与 `lifespan` 里 `create_all` 建表并存（见下）。
6. **分页/性能缺口**：多数列表端点 N+1（`screen.py run_results`、`talent.py _pool_out`、`requirements.py _out_with_counts` 逐行 `db.get`）；`/stats` 全表加载后 Python 计数；前端 `ScreeningResultView` 对每个 run 串行 await。

## 四、项目地图（九区域通读）

### 4.1 规范层（specs/）

- **PRD.md**：唯一业务基准，8 个功能（F-01~F-08）+ 认证/简历两张状态表 + LLM 契约红线；5 张界面原型图全是飞书带 authcode 的时效链接，**脱离飞书实际不可用**。
- **TECH_ARCHITECTURE.md**：架构原则（提取/决策分离、统一契约、可追溯）写得好，但 §三的代码树还停在单服务时代。
- **DEPLOYMENT.md**：CI/CD 与迁移/回滚约定（破坏性迁移拆多阶段、健康检查只回滚镜像不降级数据库）——边界约束写得清楚。
- **API 分册**（specs/api/5 份）：严格区分“目标设计”与“已实现”，自曝缺口（confirm 未校验版本等）。**最新漂移**：声称 `/api/auth/*` 不存在（已实现）；完全没覆盖已存在的 `/api/tasks` 9 端点（含 SSE 流式与 action 审批）与 `/api/agent/chat`；feature_03 引用废弃路径 `POST /api/batches`（实际是 `/api/resumes/upload`）。
- **已确认待办口径**：错误码无统一信封（调用方只能拿中文 detail）、多数列表无分页协议、批次进度不持久化已写进 conventions.md。

### 4.2 主服务业务逻辑层（app_service/services + clients，13 模块 + 3 客户端）

核心流水线：`upload_service`（SHA256 全库去重、落 `<sha256>.pdf`）→ `pipeline`（批次编排、状态机流转、内存进度表）→ `normalize_service`（NFKC + LLM 提取 + 双校验 + 2 次重试）→ `assign_service`（幂等全量分配，无评分无淘汰）→ `screen_service`（三态规则引擎）→ 多岗归并更新简历状态。

四个宪法未承认的子系统：

- **只读招聘 Agent**（agent_service）：四标签意图路由（LLM 分类 + 枚举白名单 + 关键词兜底，永不误拒）→ 工具循环（最多 6 轮）：知识库检索 / safe_text2sql 查询 / 人岗评估（回调确定性 evaluate_profile）/ 邀约提案（只建议不执行）；
- **任务审批持久化**（task_service）：消息/工具 trace 落库，提案进 pending AgentAction，审批时全量复核快照；
- **认证**（auth_service）：行锁 + 失败锁定 + dummy 哈希防枚举 + 哈希 token；
- **人才知识同步**（talent_knowledge_service）：白名单脱敏 → PUT 知识库幂等覆盖，失败置 failed 可重试、不回滚沉淀事务；另有离线 `knowledge_export` CLI 导 Dify markdown + PII 单独索引 CSV。

客户端层三件套均手动重试 + 退避 + 语义化异常（parser 对 422 不重试、knowledge 对 429/5xx 重试）。

### 4.3 主服务 API/数据层

`app.py` 工厂注册 9 组路由前缀（auth/resumes/parse/requirements/jobs/screening/talent/agent/tasks），lifespan 里 init 日志 + `create_all` 建表 + seed 管理员。**发现**：api 层多处直接操作 ORM 属越层（见 2.2-2）；`core/identity.py` 的 `get_trusted_actor` 仍返回 `default_hr_id` 而非从已认证会话取用户（注释自认待迁，`request.state.auth_user` 已就位却没接上）——upload 仍接受表单 `hr_id`，操作人可伪造；默认管理员密码 `Resume@2026` 硬编码在 `core/config.py` 默认值里；`config.py` 注释写 5M、默认值 10MB；auth 中间件每请求新开 SessionLocal。

### 4.4 前端（services/app/web）

11 条懒加载路由 + 登录守卫；上传页 keep-alive 保切换不丢状态、前端三重校验（.pdf/≤5M/去重）；筛选结果页是核心复杂度所在（按候选人聚合多岗 run、请求序号防“后发先至”、四态卡汇总）；两套聊天 UI（KnowledgeView 与 TaskConversation）几乎同构但**各写一份 SSE/审批逻辑**，改协议要改两处；SSE 用原生 fetch 手写 reader 绕过 axios 拦截器，401 语义靠人工双处同步；无 Pinia、无前端测试（package.json 无 test 脚本）。匹配度弹窗“—建设中”是合规占位，未私建 match_score。无状态管理库当前可辩护（页面间数据独立），但聊天双份 + SSE 双处是最该抽的公共层。

### 4.5 解析服务（services/parser）

最符合宪法的一个服务：严格四层、无 DB、无状态。三级降级链（PyMuPDF → pdfplumber → 150dpi PNG 视觉 OCR）以 `min_effective_chars` 为闸门，warnings 记录每级失败原因；OCR prompt 明令“只转写可见文字、不解释不推断”，VisionClient 空返回抛错。契约测试直接对黄金样本断言（S01 不走 OCR、S05 扫描件走 OCR、S09 加密 422、S10 损坏必失败不静默成功）。小瑕疵：OCR 全失败抛未捕获异常 → 500，app 侧统一归类“解析服务不可用”（已文档化的折中）；OCR 重试循环里重复实例化 VisionClient，配置缺失时也会空转重试。

### 4.6 知识库服务（services/knowledge）

链路：脱敏画像 PUT → LLM 生成卡片字段（过 `extra='forbid'` 校验，失败即阻断）→ 渲染 Wiki 卡片 markdown（frontmatter 五字段）+ 落 md 副本供人读/git 管理 → chunker（剥 frontmatter、按标题 + 550 字/80 重叠回退）→ Chroma cosine 索引（upsert 先 delete 保幂等）。检索：全量切片 jieba 重建 BM25 + 稠密召回各取 15，RRF(k=60) 融合，rerank 输出证据块。离线评测器（knowledge-eval CLI）直连服务产出 hit@k / MRR / 拒答率报告。

**实测问题**（见第五节）：`wiki_card.py:71` 引用不存在的 `settings.model_timeout_seconds`（AttributeError 被吞掉）；本地 chroma 索引（75 片、人名做 talent_card_id）与 `data/wiki`（22 张旧版格式）、黄金集三方漂移，反映的是历史落点；每次查询全量拉取重建 BM25 无缓存（O(语料)）；线上检索不做拒答（阈值只在离线评测用）；`metadata_filter` 是半成品（入库端装配、检索端不接收）。

### 4.7 测试与迁移（services/app/tests + migrations）

## 附录 B：读者结论冲突裁决二则

### B1 alembic 迁移 vs create_all（已裁决并有实锤）

- **冲突**：API/数据层读者断言“无迁移工具，仅靠 create_all”；测试读者与工程配置读者给出 5 版迁移史与 CI 命令。

- **权威性定论**（补读实证）：**alembic 是唯一权威，`init_db` 的 `create_all` 是“只建缺失表、从不 ALTER”的兜底**。部署顺序下（先迁移后起容器）它对迁移建好的库是恒等 no-op，不构成第二套 schema 来源。**但存在真实的链路破坏机制**：按 AGENTS.md 从根直接 uvicorn 时没有迁移步骤，`create_all` 在空库建出 head 形态但没有 `alembic_version` 记录——此后在同一库跑 `alembic upgrade head`，0001 幂等（IF NOT EXISTS）可通过，但后续含裸 `RENAME` 的 0003（20261023）将因目标列已存在而报错断裂；且目前**没有任何门禁能发现这种漂移**。建议：`create_all` 降级为仅测试初始化，或起服前强制 `alembic stamp head`。

### B2 多岗汇总是否校验联系方式（双方都“对”，错在代码）
