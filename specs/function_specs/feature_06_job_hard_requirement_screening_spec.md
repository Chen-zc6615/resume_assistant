# 功能六 根据岗位硬性条件初筛

版本：v1.1 草案｜日期：2026-10-14｜实现状态：与当前确定性规则引擎对齐。

## 1. 目标与输入

对每个有效的“简历—岗位”组合独立执行岗位硬性条件初筛，输出通过、不通过或待人工复核结论及逐项原因。筛选结论不改变简历事实，也不自动将简历写入人才库。

输入包括岗位组关联、已经校验的归一化简历以及岗位当前硬性条件。大模型不得参与淘汰决策；岗位 JD、加分技能和加分项不作为一票否决依据。

## 2. 规则契约

| 硬性条件 | 判断规则 | 信息缺失处理 |
| --- | --- | --- |
| 最低学历 | 简历学历等级不低于岗位要求 | 学历缺失或无法映射 → 待人工复核 |
| 最低工作年限 | `total_work_months >= job_min_exp_years × 12` | 工作月数无法确定 → 待人工复核 |
| 必备技能 | 岗位要求的每项技能均须命中 | 简历完全没有可判断的技能信息 → 待人工复核；存在技能信息但缺少必备技能 → 不通过 |
| 加分技能与加分项 | 仅展示命中情况 | 不影响硬性初筛结论 |

最低学历、最低年限或必备技能未配置时，对应规则视为不限并记录通过原因。规则之间采用 AND：任一明确不满足则不通过；没有明确不满足但存在信息不足则待人工复核；全部满足或均不限则通过。

技能匹配采用确定性的规范化、显式别名及受控模糊匹配规则。调整技能别名或匹配阈值时必须通过测试固定边界，不能改用模型自由判断。

## 3. 输出契约

每个岗位筛选结果保存：筛选任务、简历、归一化画像、结果、逐项原因和执行时间。结果枚举为：

| 结果 | 含义 |
| --- | --- |
| PASS | 所有已配置硬性条件均满足 |
| REJECT | 至少一项条件有明确证据表明不满足 |
| PENDING_REVIEW | 没有明确不满足，但信息不足，无法自动判断 |

逐项原因至少包含规则名称、是否满足和说明。信息不足不得写成候选人确定不具备相关能力，也不得直接转换成 `REJECT`。

## 4. 执行与留痕

系统按岗位创建筛选任务并保存执行时刻的规则快照。模板或岗位条件之后发生变化，不得回写历史筛选依据；重新筛选产生新的任务和结果。

同一份简历在不同岗位拥有独立结果。一个岗位不通过不能阻止该简历继续参与同一需求下其他岗位的筛选。全部岗位完成后，由功能七统一汇总当前有效岗位的最新结果。

筛选任务执行失败属于系统异常，应记录失败并允许重试，不得当成业务不通过。已完成入库的简历不被后续筛选覆盖。

## 5. 接口与界面

自动流程在岗位分配后按岗位触发筛选；岗位组可通过 `POST /api/jobs/{job_id}/screen` 手动重筛。筛选结果查询展示规则快照、逐条判定原因以及对应岗位。

界面必须区分“明确不符合”“信息不足待复核”和“执行失败”，不能只用一个失败标签概括。

## 6. 验收标准

- 本科满足最低本科，大专不满足最低本科，学历缺失进入待人工复核。
- 24 个月满足两年要求，23 个月不满足，工作月数未知进入待人工复核。
- 必备技能全部命中才通过；加分技能缺失不影响结论。
- 同一简历在两个岗位可以分别产生不同结果，互不覆盖。
- 前一岗位不通过不妨碍后续岗位执行。
- LLM 不参与任何淘汰判断，系统异常不记为业务不通过。
