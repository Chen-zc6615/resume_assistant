# 功能一 需求与岗位管理

版本：v1.0 草案｜日期：2026-10-09｜用途：七功能流程的产品、开发与验收依据。

## 1. 目标与范围

HR 先维护招聘需求，再维护该需求下的岗位及各岗位硬性条件，为需求初筛、岗位分配和岗位初筛提供可追溯的结构化依据。

七功能主流程：需求与岗位管理 → 上传简历解析简历 → 简历归一化 → 根据需求简历初筛 → 岗位分配 → 根据岗位硬性条件初筛 → 简历审核与入人才库。失败记录可以提前转人工处理，但不能绕过最终人工确认入库。

本规格中的新增实体、接口和状态为目标设计，不代表已实现。参考现有 `src/models/schemas.py`、`src/models/db_models.py`、`src/api/screen.py` 和旧版功能 SPEC。项目约定引用的 `PRD.md`、`SPEC_DATA_MODELS.md`、`TECH_ARCHITECTURE.md` 当前缺失；旧资料含义不一致处在本组文档中说明，不擅自视为已定规则。

## 2. 业务边界

- 需求代表一次招聘任务或招聘范围；岗位代表需求内具体职位。目标关系为一个需求包含多个岗位，一个岗位归属一个需求。
- 需求条件用于判断候选人是否进入该需求的岗位分配环节；岗位硬条件用于判断具体候选人与岗位组合是否符合要求。
- 自然语言描述用于展示和解释，只有 HR 确认的结构化条件可参与自动筛选。
- 不自动生成匹配分数、排名权重或格式化导出规则。人数、优先级、截止时间等扩展字段待业务确认。

## 3. 数据契约

| 实体/字段 | 类型 | 约束与含义 |
| --- | --- | --- |
| Requirement.requirement_id | 非空字符串 | 唯一、不可变 |
| requirement_name / description | 非空字符串 | 需求名称、需求说明 |
| status | draft / active / closed | 草稿、启用、关闭 |
| version | 正整数 | 每次修改影响筛选的内容时递增 |
| criteria | 条件数组 | 字段、运算符、目标值；每条有稳定 criterion_id |
| created_by / updated_by | 用户标识 | 由可信用户上下文提供 |
| created_at / updated_at | 时间戳 | 服务端记录 |
| Job.requirement_id | 非空字符串 | 新增外键，指向所属需求 |
| job_id / job_name / job_jd | 非空字符串 | 沿用现有 Job 契约 |
| job_min_degree | 大专 / 本科 / 硕士 / 博士 / null | null 表示不限 |
| job_min_exp_years | 非负整数 / null | 0 或 null 表示不限 |
| job_required_skills | 字符串数组 | 所有条目均须满足，无空字符串 |
| job_optional_skills | 字符串数组 | 展示用，不决定通过、不自动计分 |
| job_status | 0 / 1 / 2 | 目标统一为草稿 / 在招 / 关闭 |
| Job.version | 正整数 | 用于筛选与分配追溯 |

需求条件首期仅允许 `highest_education` 的最低学历比较、`total_work_months` 的非负整数下限、`skills` 的全部包含比较。HR 可留空条件；其他条件须先定义字段来源和比较规则，再扩展允许列表。不得把描述中的要求静默转换成已生效条件。

## 4. 操作与状态

1. HR 创建草稿需求，填写名称、描述和结构化条件。
2. HR 在需求下创建岗位，填写 JD 和硬条件，检查数据合法性。
3. 启用需求后可上传关联简历；仅在招岗位可以接受新的岗位分配。
4. 修改条件生成新版本；旧筛选结果保留原版本，并标记需要重筛。
5. 关闭需求阻止新上传、新分配和新筛选任务；历史记录继续可读。重新启用保留原历史。

岗位状态操作必须独立于岗位内容编辑，避免普通保存误改招聘状态。关闭存在历史记录的需求或岗位不得级联删除简历、结果、审核记录。

## 5. 接口与界面

目标接口：`POST/GET /api/requirements`、`GET/PUT /api/requirements/{requirement_id}`、`PATCH /api/requirements/{requirement_id}/status`。岗位沿用 `POST/GET /api/jobs`、`PUT /api/jobs/{job_id}`、`PATCH /api/jobs/{job_id}/status`，新增需求关联和版本字段。更新携带 expected_version，冲突返回 409；缺失记录返回 404；非法字段返回 422。

界面提供需求列表、需求详情、所属岗位列表、条件编辑与状态切换；明确区分需求条件与岗位硬条件。条件为空时显示“未设置筛选条件”。

## 6. 一致性与迁移

需求、岗位修改与版本更新在同一事务提交。筛选保存规则快照，不能通过覆盖岗位配置改写历史结论。所有产品实现位于 `src/`。

现有批次仅关联 job_id，没有需求实体；迁移须经 HR 确认历史岗位与需求映射，不根据岗位名称自动推测归属。旧文档将岗位状态 0 定义为草稿，现有 API 注释将其称为停用；上线迁移前统一前端文案及历史含义。

## 7. 验收标准

- 一个需求能维护多个岗位，不存在的需求不可绑定。
- 无效学历、负数年限、空技能条目和重复标识被拒绝。
- 修改 JD 不自动新增硬条件；加分技能不参与拒绝判断。
- 修改条件后旧结果仍可查看，并可识别所用版本及失效原因。
- 关闭需求阻止新增处理但保留历史；并发编辑不能覆盖他人变更。
