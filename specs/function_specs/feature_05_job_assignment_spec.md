# 功能五 岗位分配

版本：v1.0 草案｜日期：2026-10-09｜实现状态：新增目标设计。

## 1. 目标与默认方式

把需求初筛通过的简历关联到该需求下的具体在招岗位，为岗位硬条件初筛建立明确输入。分配表示进入该岗位评估，不表示满足岗位条件，也不表示人才入库。

自动推荐和匹配评分规则尚未确定，首期目标采用 HR 手动分配，可批量操作。目标支持一份简历分配到同一需求下多个岗位，每个组合独立筛选；如业务要求单岗位分配，应在实现前收紧约束。不得自行采用关键词相似度或模型分数自动决定分配。

## 2. 前置条件与实体

前置条件：需求启用；岗位属于该需求且在招；归一化草稿合法；需求初筛存在未过期的 passed 结果。需求待核对、不通过或执行失败均不能直接新建分配。

| JobAssignment 字段 | 类型与含义 |
| --- | --- |
| assignment_id | 唯一标识 |
| requirement_id、resume_id、job_id | 外键，所属需求一致 |
| requirement_screen_result_id | 引用通过的需求初筛结果 |
| normalization_version、job_version | 分配所用输入版本 |
| status | active / cancelled / stale |
| assigned_by、assigned_at | HR 标识与服务端时间 |
| cancelled_by、cancelled_at、cancel_reason | 取消信息，可为空 |

同一 requirement_id、resume_id、job_id 仅允许一条 active 分配。取消后重分配创建新历史记录或新版本，不删除已发生的审核和筛选记录。

## 3. 流程与状态

1. HR 从需求初筛通过列表选择简历。
2. 系统只展示所属需求下的在招岗位，同时展示 JD 和硬条件。
3. HR 选择一个或多个岗位；服务端重新检查状态、归属与版本。
4. 保存分配，生成每个简历—岗位组合的待筛选任务。
5. 进入功能六，每个分配独立得到结论。

未分配简历保持“待岗位分配”，不能显示岗位筛选通过。取消分配后停止该组合的新任务，运行中任务若完成仍可保留历史，但不能作为当前有效审核依据。需求结果失效、岗位条件变化或归一化版本变化时，分配标记 stale，重新验证前置条件后生成新的筛选任务。

更换岗位通过取消旧关联并新建关联完成；其他岗位的有效关联不受影响。关闭岗位阻止新分配，历史分配继续可读。

## 4. 接口与一致性

目标接口：`POST /api/assignments`，请求含 requirement_id、resume_ids、job_ids、expected_versions；`GET /api/assignments` 支持按需求、岗位、简历和状态查询；`POST /api/assignments/{assignment_id}/cancel` 记录原因。

批量请求以每个简历—岗位组合为事务边界，返回 created、existing、failed 和对应原因；界面明确显示部分成功。唯一约束防止并发重复关联；重复提交相同有效分配返回已有记录。状态或版本变化返回 409，不静默绑定最新规则。操作者来自可信上下文。

## 5. 界面要求

提供待分配列表、简历事实预览、可选岗位和已分配岗位标签；展示每个组合的分配及筛选状态。批量操作前显示简历数、岗位数和组合数，避免用户误解多岗位操作的范围。此处不展示未经定义的匹配分数。

## 6. 验收标准

- 同需求在招岗位可以分配，跨需求、关闭岗位和过期需求结果被拒绝。
- 同一简历可产生多个独立岗位结果，不能只用一个全局 screen_status 覆盖。
- 重复点击、并发分配不会创建重复 active 关联。
- 取消某岗位分配不影响其他分配，历史记录仍可查询。
- 一部分组合失败时返回具体失败项，成功项可继续岗位筛选。
- 未分配、失效和已取消组合不能作为当前入库审核依据。
