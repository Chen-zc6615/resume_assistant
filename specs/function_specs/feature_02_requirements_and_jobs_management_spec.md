# 功能二 需求与岗位管理

版本：v1.0 草案｜日期：2026-10-09｜用途：八功能流程的产品、开发与验收依据。

## 1. 目标与范围

HR 先维护招聘需求，再维护该需求下的岗位及各岗位硬性条件，为岗位分配、逐岗位初筛和多岗位结果汇总提供可追溯的业务上下文。

八功能主流程：用户登录 → 需求与岗位管理 → 上传简历解析简历 → 简历归一化 → 岗位分配 → 根据岗位硬性条件初筛 → 多岗位筛选结果汇总 → 简历审核与入人才库。失败记录可以提前转人工处理，但不能绕过最终人工确认入库。

本规格中的新增实体、接口和状态为目标设计，不代表已实现。上层业务范围以 `PRD.md` 为准，工程边界以 `TECH_ARCHITECTURE.md` 为准；实现时同时核对现有 `src/models/schemas.py`、`src/models/db_models.py` 和 `src/api/screen.py`，不把目标设计误写成已实现能力。

## 2. 业务边界

- 需求代表一次招聘任务或招聘范围；岗位代表需求内具体职位。目标关系为一个需求包含多个岗位，一个岗位归属一个需求。
- 招聘需求是岗位集合容器，自身不设置最低学历、工作年限或必备技能等筛选条件。
- 需求名称和说明用于组织招聘任务与展示上下文；只有岗位中由 HR 确认的结构化硬性条件参与自动筛选。
- 不自动生成匹配分数、排名权重或格式化导出规则。人数、优先级、截止时间等扩展字段待业务确认。

## 3. 数据契约

| 实体/字段 | 类型 | 约束与含义 |
| --- | --- | --- |
| Requirement.requirement_id | 正整数 | 唯一、不可变 |
| requirement_name / description | 非空字符串 | 需求名称、需求说明 |
| status | 0 / 1 | 进行中 / 已关闭 |
| created_by | 用户标识 | 由可信用户上下文提供 |
| created_at / updated_at | 时间戳 | 服务端记录 |
| Job.requirement_id | 正整数 | 外键，指向所属需求 |
| job_id / job_name / job_jd | 岗位标识与文本 | 沿用现有 Job 契约 |
| job_min_degree | 大专 / 本科 / 硕士 / 博士 / null | null 表示不限 |
| job_min_exp_years | 非负整数 / null | 0 或 null 表示不限 |
| job_required_skills | 字符串数组 | 所有条目均须满足，无空字符串 |
| job_optional_skills | 字符串数组 | 展示用，不决定通过、不自动计分 |
| job_status | 0 / 1 / 2 | 目标统一为草稿 / 在招 / 关闭 |

需求说明中的自然语言不得被静默转换为筛选条件。筛选规则只取自对应岗位的结构化字段，并在执行时保存快照。

## 4. 操作与状态

1. HR 创建招聘需求，填写名称、部门、截止日期和说明。
2. HR 在需求下创建岗位，填写 JD 和硬条件，检查数据合法性。
3. 启用需求后可上传关联简历；仅在招岗位可以接受新的岗位分配。
4. 修改岗位硬性条件后重新执行相关岗位筛选；旧结果和规则快照继续保留。
5. 关闭需求阻止新上传、新分配和新筛选任务；历史记录继续可读。重新启用保留原历史。

岗位状态操作必须独立于岗位内容编辑，避免普通保存误改招聘状态。关闭存在历史记录的需求或岗位不得级联删除简历、结果、审核记录。

## 5. 接口与界面

需求使用 `POST/GET /api/requirements` 和 `GET/PUT /api/requirements/{requirement_id}` 管理；岗位使用 `POST/GET /api/jobs` 和 `PUT /api/jobs/{job_id}` 管理。缺失记录返回 404，非法字段返回 422；状态与并发更新约束以后端契约为准。

界面提供需求列表、需求详情、所属岗位列表和状态切换。岗位硬性条件在岗位编辑区维护；需求页面不得出现容易被误认为独立筛选规则的“需求条件”。

## 6. 一致性与迁移

需求和岗位修改分别在事务中提交。筛选保存岗位规则快照，不能通过覆盖岗位配置改写历史结论。所有产品实现位于 `src/`。

上传批次通过需求池关联招聘需求；岗位必须归属于一个需求。历史数据迁移不得根据岗位名称自动推测归属。岗位状态统一为 0 草稿、1 开放、2 关闭。

## 7. 验收标准

- 一个需求能维护多个岗位，不存在的需求不可绑定。
- 无效学历、负数年限、空技能条目和重复标识被拒绝。
- 修改 JD 不自动新增硬条件；加分技能不参与拒绝判断。
- 修改岗位硬性条件后可以重筛，旧结果和执行时规则快照仍可查看。
- 关闭需求阻止新增处理但保留历史；并发编辑不能覆盖他人变更。
