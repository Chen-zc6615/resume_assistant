# **一、系统总体架构**

## **1\.1 系统目标**

系统面向 HR 招聘业务，将不同版式的 PDF 简历转换为统一的候选人画像，依据岗位硬性条件完成初筛，并支持人工审核、面试记录和人才沉淀。

系统由前端交互、后端业务、外部模型接入和本地数据存储四部分组成。前端提供统一工作台，后端集中管理招聘业务和简历处理，模型服务提供文本与视觉识别能力，数据库和文件目录分别保存结构化信息与原始材料。

## **1\.2 架构原则**

- **轻量部署：**采用模块化单体架构。前端与后端分开开发，后端业务模块在同一应用中运行，适合当前单机、低并发的使用规模。

- **职责分离：**接口层负责接收请求和组织响应；业务服务分别处理文件、解析、归一化、分配与筛选；模型与存储通过专门模块接入，避免页面承担业务决策。

- **提取与决策分离：**大模型负责从非结构化材料中提取信息，确定性规则负责自动初筛，HR 负责对需要人工判断的内容审核。这使筛选依据可以复查。

- **统一数据契约：**后端使用 Pydantic 定义业务数据，模型输出经过 JSON Schema 和实体校验后再写入画像，减少字段含义和格式不一致的问题。

- **过程可追溯：**原始文件、分组来源、筛选规则快照与判定原因分别保留，支持 HR 对照原文查看结果。

## **1\.3 总体架构图**

系统采用 **Vue 前端 \+ FastAPI 后端 \+ PostgreSQL 数据库 \+ 本地文件存储**，通过外部模型服务完成视觉识别与结构化提取。

需求与岗位管理提供招聘业务上下文，简历处理流水线组织自动处理能力，人工审核与人才管理承接需要 HR 决定的事项。三个业务区域共享同一套简历和岗位数据，避免在不同页面维护互不一致的候选人副本。

# **二、技术选型**

## **2\.1 前端**

前端是 HR 的统一操作入口，既要展示需求和岗位信息，也要处理批量上传、任务进度、筛选结果和原文对照审核。因此选型侧重表单与表格能力、页面组织和接口数据一致性。

|类别|选型|选型理由|
|---|---|---|
|应用框架|Vue 3 \+ TypeScript|组合式 API 便于拆分页面逻辑；类型定义约束简历、岗位和筛选结果的前端表示|
|UI 组件|Element Plus|上传、表格、表单、抽屉和弹窗可覆盖主要 HR 操作场景，减少通用控件开发|
|样式|Tailwind CSS \+ 自定义 CSS|用工具类统一布局，同时保留页面和组件的局部样式定制|
|构建工具|Vite|支持开发热更新、接口代理和静态资源构建|
|路由|Vue Router|管理工作台、上传、结果和人才等页面，按路由加载页面组件|
|HTTP 客户端|Axios|集中设置 API 基础路径、请求超时和后端错误信息处理|

前端业务页面、复用组件、请求封装和数据类型分别组织。页面负责用户交互，接口封装负责调用后端；筛选规则和候选人状态的最终判断仍由后端提供。

## **2\.2 后端与存储**

后端以 FastAPI 组织 HTTP 入口，使用 SQLAlchemy 管理业务数据，并通过业务服务隔离模型调用、文件处理和初筛判断。结构化业务数据保存到 PostgreSQL，原始 PDF 保存到服务器本地挂载目录；数据库连接由 `DATABASE_URL` 统一配置。

|类别|选型|选型理由|
|---|---|---|
|开发语言|Python 3\.12\+|与 PDF 处理、模型调用、数据校验和规则处理所用库相配合|
|Web 服务|FastAPI \+ Uvicorn|统一暴露业务接口，支持参数校验、依赖注入和 OpenAPI 文档生成|
|数据校验|Pydantic v2 \+ JSON Schema|分别约束业务实体和模型输出结构；不把模型返回内容直接视为可信数据|
|数据访问|SQLAlchemy 2|统一定义实体关系、查询和事务，减少业务模块对具体 SQL 的依赖|
|数据库|PostgreSQL 17 \+ psycopg 3|提供事务、约束和并发访问能力；生产与测试数据库通过 Docker Compose 分别运行|
|文件存储|本地目录|将原始 PDF 与业务记录分开保存，便于预览、复核和重新解析|
|后台处理|FastAPI BackgroundTasks|上传请求返回后在应用进程内处理任务，无需另建队列服务|
|模型接入|OpenAI Python SDK，连接 DashScope 兼容接口|由统一客户端封装文本模型和视觉模型，避免业务模块直接拼接模型请求|

后台任务与进度数据依赖当前应用进程，因此这是单实例处理架构。数据库和原始文件是持久化数据；批次进度不是持久任务记录。后续如需多实例处理，应先解决任务分发与进度共享，而不能仅增加应用进程数。

## **2\.3 解析、归一化与筛选**

简历输入可能是可复制文本、复杂排版或扫描件，单一文本提取方式无法覆盖这些情况。系统将文档读取、模型抽取和规则判断作为不同能力，分别选择适合的工具。

|环节|选型|设计理由|
|---|---|---|
|PDF 文本提取|PyMuPDF \+ pdfplumber|前者承担主要文本提取，后者在文本不足时补充不同布局的提取能力|
|扫描件识别|qwen\-vl\-max|将页面图片识别为文字，补充无有效文本层的 PDF|
|文本预处理|Unicode NFKC \+ 正则|统一字符形式并清理控制字符、多余空白，减少格式差异|
|结构化提取|qwen\-plus|将非统一格式文本整理为约定的基本信息、技能和经历结构|
|技能归一|本地技能别名字典|将已知缩写和写法变体映射到一致名称，保持筛选口径稳定|
|技能匹配|关键词、别名及 RapidFuzz|在标准写法之外处理部分拼写和组合表述差异|
|硬性初筛|数据库取数 \+ Python 规则引擎|分离候选集查询与规则判定，便于形成三态结果和逐项原因|

归一化后的画像采用固定数据契约，模型输出先通过结构校验和实体校验，再供筛选使用。岗位分配面向需求下的全部开放岗位；学历、年限和必备技能由规则引擎判断。当前主链不依赖公司学校主数据平台、向量数据库或语义召回模型，岗位分配和自动淘汰也不使用大模型评分。
