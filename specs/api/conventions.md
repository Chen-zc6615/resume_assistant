# API 公共约定

## 协议与数据格式

- 除文件上传和文件下载外，请求与响应使用 JSON。
- 批量上传使用 `multipart/form-data`；PDF 预览返回 `application/pdf`；筛选导出返回 `text/csv`。
- 日期字段目前多为字符串。年月采用 `YYYY-MM`，需求截止日期约定为 `YYYY-MM-DD`。
- 数据库 ID 为正整数；知识库 `document_id` 为调用方指定的字符串。
- 列表接口当前没有统一分页协议。仅部分接口提供 `limit`，详见具体端点。

## 成功与错误

大多数创建、更新和动作接口当前返回 `200 OK`；知识库删除接口返回 `204 No Content`。删除类主服务接口通常返回：

```json
{"ok": true}
```

FastAPI 显式业务错误使用标准 `detail` 结构：

```json
{"detail": "简历不存在"}
```

请求字段校验失败返回 `422`，其 `detail` 是 FastAPI/Pydantic 的错误数组。常见状态码：

| 状态码 | 含义 |
| --- | --- |
| `200` | 请求成功 |
| `204` | 删除成功且无响应体 |
| `400` | 当前业务状态不允许操作，或缺少可处理数据 |
| `404` | 资源不存在 |
| `409` | 唯一性或业务状态冲突 |
| `422` | 请求字段或上传文件校验失败 |
| `503` | 下游知识库暂时不可用 |

当前尚未定义统一的业务错误码和错误信封，调用方不要依赖中文 `detail` 文本进行长期稳定的程序分支。

## 认证与操作人

当前代码尚无 `/api/auth/login`、`/api/auth/me` 和 `/api/auth/logout`，也没有统一的受保护路由依赖。

| 接口区域 | 当前操作人来源 |
| --- | --- |
| 简历上传 | 表单 `hr_id`，为空时使用服务端 `DEFAULT_HR_ID` |
| 需求、岗位、筛选模板 | 部分请求体仍含 `created_by` / `job_created_by` |
| 手工加入需求池或岗位组 | 代码中的过渡值 `hr_admin` |
| 面试邀约、人才库沉淀 | 服务端 `DEFAULT_HR_ID`，客户端不能覆盖 |

因此这些字段目前只用于留痕，不构成可靠鉴权。目标实现是由服务端会话提供可信用户身份，并移除或忽略客户端操作人字段。

## 简历状态

`resumes.status` 的当前枚举：

| 值 | 标签 | 含义 |
| ---: | --- | --- |
| `0` | 上传失败 | 文件接收阶段失败 |
| `1` | 解析失败 | 文本提取/OCR 失败 |
| `2` | 归一化失败 | 结构化提取或校验失败 |
| `3` | 初筛不通过 | 规则淘汰或人工筛除 |
| `4` | 已完成 | HR 已确认完成 |
| `5` | 待补录 | 已有通过岗位，但电话或邮箱缺失 |
| `6` | 待人工复核 | 无明确不合格项，但信息不足 |
| `7` | 待解析 | 上传成功，等待解析 |
| `8` | 待归一化 | 解析成功，等待归一化 |
| `9` | 待初筛 | 归一化成功，等待岗位筛选 |
| `10` | 待审核入库 | 至少一个岗位通过，等待 HR 确认 |

筛选结果为 `PASS`、`REJECT` 或 `PENDING_REVIEW`。任一岗位通过优先于其他岗位不通过；信息不足不得直接转换成 `REJECT`。

面试状态为：`0` 待面试、`1` 已邀请、`2` 面试中、`3` 已入职、`4` 暂不跟进。

## 幂等性与副作用

- PDF 按 SHA-256 全局去重；重复上传复用已有 `resume_id`。
- 把简历加入需求池或岗位组时，已存在的关系会跳过并计入 `skipped_duplicated`。
- 人才库按简历唯一；重复沉淀当前返回 `409`，不是成功响应。
- `PUT /api/v1/documents/{document_id}` 和人才画像写入按 `document_id` 覆盖，适合重试。
- 上传处理使用进程内后台任务，批次进度不持久化；应用重启后可能无法继续查询旧 `batch_id`。

## 隐私与服务边界

主服务向知识库同步的是脱敏归一化画像，不包含电话、邮箱、PDF 原文/路径或 HR 内部备注。知识库不是招聘业务数据的真理之源；同步失败不会回滚已经成功的人才库沉淀。
